## Хеш-таблицы

В `HashMap` хешер вычисляет число из ключа, а таблица выбирает слот. Rust позволяет поменять хешер и оставить тот же `HashMap`. Я использовал это, чтобы сравнить два варианта на одних и тех же целых ключах.

### Что делает `get`

В стандартной библиотеке Rust `HashMap` использует Swiss Table из `hashbrown`. Хеш задаёт стартовую позицию и семибитную метку H2. Таблица читает группу компактных меток и проверяет `Eq` только для слотов с подходящей H2. Если ни один ключ не подошёл, пустой слот завершает поиск. При отсутствии пустых слотов поиск переходит к следующей группе. Маркер удаления разрешает продолжить поиск. [Документация `HashMap`](https://doc.rust-lang.org/std/collections/struct.HashMap.html) · [Схема поиска Swiss Table](https://abseil.io/about/design/swisstables)

Rust 1.98 использует `hashbrown` 0.17.1. На Apple Silicon его ветка NEON читает восемь меток за раз. На x86 с SSE2 группа шире - 16 меток. [Зависимости стандартной библиотеки](https://github.com/rust-lang/rust/blob/1.98.0/library/Cargo.lock) · [Выбор реализации группы](https://github.com/rust-lang/hashbrown/blob/v0.17.1/src/control/group/mod.rs) · [Группа NEON](https://github.com/rust-lang/hashbrown/blob/v0.17.1/src/control/group/neon.rs)

Смысл H2 в том, чтобы меньше читать сами ключи. При равномерных метках произвольный занятый слот проходит фильтр примерно в одном случае из 128. Если у ключей одинаковые H2, этот фильтр перестаёт экономить сравнения внутри группы.

Для пользовательских ключей `Eq` и `Hash` обязаны согласоваться. Если два ключа равны, их хеши должны совпадать. При совпадении хешей разных ключей окончательное решение принимает `Eq`. [Контракт `Hash`](https://doc.rust-lang.org/std/hash/trait.Hash.html#hash-and-eq)

### Что меняется при смене хешера

Хешер по умолчанию в Rust 1.98 - SipHash 1-3 со случайным начальным состоянием `RandomState`. Он затрудняет подбор коллизий, когда ключи приходят извне. API `BuildHasher` позволяет выбрать другой хешер для отдельной карты. [Документация `HashMap`](https://doc.rust-lang.org/std/collections/struct.HashMap.html)

В контрольном варианте для `u32` хеш равен самому ключу. Это убирает вычисление SipHash и одновременно меняет раскладку таблицы. Здесь `hashbrown` берёт H2 из семи старших битов 64-битного хеша, а начальный слот выбирает по младшим битам. Ключи занимают 31 бит, поэтому H2 у всех записей равен нулю. Разница между вариантами включает и вычисление хеша, и раскладку. Этот контрольный хешер теряет защиту от подбора коллизий. [Метка H2](https://github.com/rust-lang/hashbrown/blob/v0.17.1/src/control/tag.rs#L29-L44) · [Старт пробирования](https://github.com/rust-lang/hashbrown/blob/v0.17.1/src/raw.rs#L52-L85)

### Вставка, удаление и запас места

`HashMap::with_capacity(n)` заранее выделяет место как минимум для `n` элементов. Это позволяет пройти известный объём без промежуточных расширений. За слишком щедрый резерв приходится платить памятью и временем обхода. `iter()` сканирует метаданные, включая пустые слоты, поэтому обход занимает `O(capacity)`. [Резерв и обход в `HashMap`](https://doc.rust-lang.org/std/collections/struct.HashMap.html)

После серии удалений полезно сравнить `len()` и `capacity()`. Таблица сама не сжимается. `shrink_to_fit()` сокращает запас настолько, насколько позволяет раскладка таблицы. `shrink_to(n)` задаёт нижнюю границу, а `clear()` сохраняет память для повторного заполнения. `BTreeMap` подходит для обхода по возрастанию ключей и запросов `range`. [Управление ёмкостью `HashMap`](https://doc.rust-lang.org/std/collections/struct.HashMap.html) · [Документация `BTreeMap`](https://doc.rust-lang.org/std/collections/struct.BTreeMap.html)

### Замеры на миллионе ключей

Mac mini M4 Pro, Rust 1.98.0. В ячейках медиана семи повторов, нс на операцию. Для каждой операции ключи подготовлены заранее. Строковый вариант хранит заимствованные `&str`, поэтому выделение памяти под строки в таблицу не попадает.

| Операция | `u32`, SipHash | `u32`, хеш равен ключу | `&str`, SipHash |
|---|---:|---:|---:|
| Вставка с нуля | 29.8 | 28.2 | 47.8 |
| Вставка с резервом | 8.4 | 12.0 | 18.8 |
| Попадание | 13.2 | 8.3 | 42.8 |
| Промах | 5.8 | 14.5 | 12.2 |
| Обход | 2.0 | 2.7 | 2.2 |
| Удаление | 14.9 | 7.9 | 46.0 |
| Смешанный поток | 24.4 | 36.9 | 110.8 |

На попаданиях вариант без SipHash сэкономил почти 5 нс. На промахах он потерял почти 9 нс, а в смешанном потоке занял в 1.5 раза больше времени. Нулевой H2 объясняет, почему после замены хешера у таблицы появляется больше кандидатов на проверку. Количество проверок `Eq` отдельно не измерял.

На заранее известном объёме резерв сократил время заполнения с SipHash примерно в 3.5 раза для `u32` и в 2.5 раза для `&str`. Время включает выделение резерва. Вставки с нуля дополнительно оплачивают расширение таблицы и перенос записей.

Смешанный поток состоит из 50% чтений, 30% записей и 20% удалений.

## Сортировки

В стандартной библиотеке Rust `sort()` сохраняет порядок элементов с равными ключами. `sort_unstable()` не даёт такой гарантии и обходится без выделения рабочей памяти в куче. В списке событий, уже отсортированном по времени, стабильная сортировка по пользователю сохранит хронологию событий каждого пользователя. В массиве `i32` равные значения неразличимы. Такой вход позволяет сравнить время работы двух алгоритмов при разном порядке и числе значений.

### За вызовами стоят два алгоритма

`sort_unstable()` в Rust 1.98 основан на ipnsort. Обычно он разбивает массив по опорному элементу, как quicksort. Если разбиения идут плохо, heapsort ограничивает время в худшем случае величиной `O(n log n)`. На полностью отсортированном входе и на строго обратном порядке достаточно линейной работы. [Документация `sort_unstable`](https://doc.rust-lang.org/std/primitive.slice.html#method.sort_unstable) · [Исходник Rust 1.98](https://github.com/rust-lang/rust/blob/1.98.0/library/core/src/slice/sort/unstable/mod.rs)

`sort()` основан на driftsort. Он сочетает стабильное разбиение со слиянием и использует уже отсортированные участки. Полностью отсортированный и строго убывающий вход он тоже обрабатывает за линейное время. На миллионе `i32` эта реализация запрашивает рабочий буфер на миллион элементов, то есть 4 МБ. Коротким срезам хватает памяти на стеке. Размер буфера следует из исходника. [Документация `sort`](https://doc.rust-lang.org/std/primitive.slice.html#method.sort) · [Исходник Rust 1.98](https://github.com/rust-lang/rust/blob/1.98.0/library/core/src/slice/sort/stable/mod.rs)

Оба алгоритма используют повторяющиеся значения. Для `k` различных ключей документация даёт ожидаемую сложность порядка `n log k` при `k` больше одного. Поэтому на миллионе элементов из тысячи значений алгоритм может сделать меньше работы, чем на миллионе почти уникальных ключей. [Сложность сортировок Rust](https://doc.rust-lang.org/std/primitive.slice.html#method.sort)

### Замеры сортировок на миллионе `i32`

Все сортировки получили одни и те же файлы из генератора `sort-bench`. `random` хранит исходную последовательность, `sorted` - её в порядке возрастания, `reverse` - в обратном порядке. В `nearly` генератор меняет местами тысячу пар в отсортированном массиве. В `few` значения лежат в диапазоне от 0 до 999.

Перед каждой сортировкой стенд восстанавливает исходный массив. Копирование и проверка упорядоченности вынесены за пределы таймера. После прогрева в 300 мс стенд собирает семь серий с целевой длительностью 200 мс. В таблице - медиана в нс на элемент.

| Распределение | Rust `sort_unstable` | Rust `sort` | C `qsort` | C++ `std::sort` | C++ `std::stable_sort` | Go `slices.Sort` |
|---|---:|---:|---:|---:|---:|---:|
| `random` | 52.4 | 58.0 | 401.8 | 84.8 | 54.0 | 314.9 |
| `sorted` | 1.4 | 1.4 | 11.3 | 4.2 | 19.5 | 2.0 |
| `reverse` | 48.6 | 27.4 | 58.9 | 6.9 | 26.9 | 2.8 |
| `nearly` | 51.4 | 89.4 | 72.8 | 19.3 | 52.2 | 45.1 |

На `random` и `nearly` быстрее оказался `sort_unstable()`. На `few` стабильная сортировка заняла 19.8 нс на элемент против 23.9 нс у нестабильной. На `reverse` разница выросла до 27.4 против 48.6 нс.

### Почему обратный порядок оказался дорогим

В `reverse` я нашёл 385 соседних пар равных значений. Rust распознаёт убывающий участок только при строгом убывании. Стабильная сортировка не может просто развернуть участок с равными элементами, потому что это изменит их взаимный порядок. Когда я подал строго убывающий ряд от 1 000 000 до 1, обе сортировки уложились в 1.7 нс на элемент. [Поиск упорядоченного участка в Rust 1.98](https://github.com/rust-lang/rust/blob/1.98.0/library/core/src/slice/sort/shared/mod.rs#L13-L45)

### Повторить замеры сортировок

Во время обоих прогонов на Mac mini работали фоновые службы. Контрольный `std::sort` на `random` занял 84.8 и 84.6 нс на элемент против 14.2 в прежней статье. Архивный бинарник на прежнем входном файле в текущих условиях дал 87.8 нс. Точную причину разницы я не установил. В таблице приведён первый свежий прогон, а повтор сохранён отдельно.

В репозитории `sort-bench` запуск описан в `rust/README.md`, результаты лежат в `results/rust-mini/`. Замеры сортировок охватывают только `i32`. Пиковую память и сохранение порядка записей с равными ключами в этой серии я не измерял.

## Перепроверка на Rust 1.100.0

Я пересобрал оба стенда официальными toolchain Rust 1.98.0 и 1.100.0 с одинаковыми флагами. На Mac mini обе версии получили те же ключи и массивы. Порядок запуска версий чередовался между конфигурациями. Для сравнения версий использую эти парные прогоны. Их абсолютные результаты заметно расходятся с предыдущей серией.

В стандартной библиотеке обеих версий используется `hashbrown` 0.17.1. Обе документируют SipHash 1-3 как хешер по умолчанию. Вместе с Rust обновился LLVM с 22.1.8 до 23.1.5. По таймингам нельзя установить, что именно дало разницу. [Зависимости Rust 1.98](https://github.com/rust-lang/rust/blob/1.98.0/library/Cargo.lock) · [Зависимости Rust 1.100](https://github.com/rust-lang/rust/blob/1.100.0/library/Cargo.lock) · [Исходник `HashMap` в Rust 1.100](https://github.com/rust-lang/rust/blob/1.100.0/library/std/src/collections/hash/map.rs)

## Вывод

**`HashMap` Rust показал лучшие медианы в обеих таблицах.** На целых ключах попадание заняло 13.2 нс против 17.6 у Bun и 23.1 у C++. В смешанном потоке Rust обошёл ближайший Go примерно в 3.6 раза. На строковых попаданиях Rust, Go и `uthash` разделили меньше 2 нс. На промахах Rust потратил 12.2 нс против 33.5 у Go и 44.5 у C++.

**В сортировках лидер менялся вместе со входом.** На случайном миллионе `i32` Rust `sort_unstable()` и C++ `std::stable_sort` уложились в 52-54 нс на элемент. На почти отсортированном массиве C++ `std::sort` был в 2.7 раза быстрее лучшего результата Rust. На обратном массиве с дубликатами Go занял 2.8 нс на элемент, Rust `sort()` - 27.4 нс.

В парном прогоне Rust 1.100.0 снизил медиану попаданий по `u32`. Время сортировки случайных `i32` изменилось меньше чем на 1%. С C++, Go и Bun я сравнивал Rust 1.98.0. В парном прогоне участвовали только две версии Rust.
