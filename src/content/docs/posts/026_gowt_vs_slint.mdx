Коллега по прошлой конторе, скинул во, похоже говорит идея на твой фреймворк, натравил агентов сравнить и вот что из этого вышло. Не сколько не претендует на сколько то объемное решение, но какие то крохи можно полезные из него получить.

[Slint](https://github.com/slint-ui/slint) - декларативный тулкит на Rust: интерфейс описывается в языке `.slint`, логика живёт в Rust (или C++, JavaScript, Python). [gowt](https://github.com/haiodo/gowt) - мой фасад над SWT на Go: виджет - это конструктор с опциями, состояние - в `rx`, на экране нативные контролы AppKit, Win32 или GTK. 

Я буду перебирать все до чего доберутся руки чтобы понять а то что у меня получилось вообще норм или не очень. Так что не обессудьте.

В общем оба фреймворка обещают одно и то же: один код, три платформы, сборка без C-тулчейна. 
Взял примеры из репозитория Slint и переписал их на GOWT. Не "по мотивам", а те же задачи с тем же поведением, чтобы сравнение было по делу.

## Что именно портировано

Из `examples/7guis` взяты пять задач: счётчик, конвертер температур, таймер, бронирование билета и рисование кругов. Как и в Slint, каждая задача - отдельная программа со своим окном: [`examples/counter`](https://github.com/haiodo/gowt/tree/main/examples/counter), [`examples/tempconv`](https://github.com/haiodo/gowt/tree/main/examples/tempconv), [`examples/timer`](https://github.com/haiodo/gowt/tree/main/examples/timer), [`examples/booker`](https://github.com/haiodo/gowt/tree/main/examples/booker), [`examples/circledraw`](https://github.com/haiodo/gowt/tree/main/examples/circledraw). Из `examples/slide_puzzle` взят пазл 15: [`examples/puzzle`](https://github.com/haiodo/gowt/tree/main/examples/puzzle).

Сразу о границах замера. Slint-примеры - исходники MIT из репозитория, версия тулкита 1.19.0, Rust 1.98. Go-версия - GOWT v0.16.3, Go 1.27.1. Всё собрано и запущено на Mac. Пазл на Go - подмножество: есть доска, ходы, анимация, reset, auto play и определение победы, но нет трёх тем, фото Берлина, шрифта Plaster и анимации "пинка" плитки. Это честно указано и в таблице строк.

## Counter: 22 строки против 29

В Slint счётчик - это одно поле и кнопка, а связь между ними выражена в самом описании:

```slint
export component Counter inherits Window {
    private property <int> value: 0;
    layout := HorizontalBox {
        LineEdit { enabled: false; text: root.value; }
        Button {
            clicked => { root.value += 1; }
            text: "Count";
        }
    }
}
```

`text: root.value` - не присваивание, а биндинг: поле перерисуется само, когда значение изменится. На Go то же самое выглядит так:

```go
func counter() gowt.Option {
	count := rx.New(0)
	value := rx.Compute(func() string { return strconv.Itoa(count.Get()) })
	return gowt.HBox(
		gowt.Text(gowt.Disabled(), gowt.Size(80, 0), gowt.BindText(value)),
		gowt.Button("Count", gowt.OnClick(func() { count.Set(count.Get() + 1) })),
	)
}
```

`BindText` в gowt принимает любое поле с `SetText`, включая `Text`, а у `Progress` есть `BindValue`: счётчик и полоска таймера подписываются одной опцией, без ручного `Watch`. Плюс десять строк `main`, которых в Slint нет: там окно создаёт viewer.

## Temperature: кто следит за циклом

В Slint каждое поле обновляет соседа прямо в обработчике:

```slint
c := LineEdit {
    text: "0";
    edited(text) => {
        if (self.text.is-float()) {
            f.text = (self.text.to-float() * 9 / 5) + 32;
        }
    }
}
```

`edited` срабатывает только на правку пользователем, поэтому присваивание в соседнее поле не возвращается обратно. В gowt v0.16.3 для этого есть `OnEdit`: он приходит на правку пользователя и не приходит на `SetText`, `Append` или запись через `Bind`. Обработчик получается такой же короткий, без флага и без риска зациклиться:

```go
setFahrenheit := func(s string) {
	v, err := strconv.ParseFloat(s, 64)
	if err != nil {
		return
	}
	fahrenheit.SetText(strconv.FormatFloat(v*9/5+32, 'f', -1, 64))
}

gowt.Text(gowt.Value("0"), gowt.Ref(&celsius), gowt.OnEdit(setFahrenheit))
```

Разница всё равно остаётся: в Slint граф зависимостей знает компилятор, а в gowt связь между полями - явный `SetText` в обработчике.

## Timer: 10 мс в двух записях

Slint:

```slint
Timer {
    interval: 10ms;
    triggered => {
        root.elapsed-time += self.interval;
        root.elapsed-time = min(root.elapsed-time, root.total-time);
    }
}
```

Go:

```go
stop := app.Every(10*time.Millisecond, func() {
	limit := total.Get() * 1000
	if elapsed.Get() >= limit {
		return
	}
	elapsed.Set(min(elapsed.Get()+10, limit))
})
```

По сути одно и то же. Разница в единицах: Slint умеет складывать `duration` и `1s`, Go хранит миллисекунды в `int` и переводит их в проценты для `Progress`. Зато в gowt полоска подписана на `rx` одной опцией: `gowt.Progress(1000, gowt.GrowX(), gowt.BindValue(progress))`.

## Flight booker: валидация в двух местах

В Slint сама форма объявляет, когда кнопка активна:

```slint
Button {
    text: "Book";
    enabled: combo.current-index != 1 ? root.validate-date(t1.text) : root.compare-date(t1.text, t2.text);
}
```

А `validate-date` и `compare-date` - это колбэки, которые Rust заполняет через `chrono`:

```rust
booker.on_validate_date(|date: SharedString| {
    NaiveDate::parse_from_str(date.as_str(), "%d.%m.%Y").is_ok()
});
```

В Go нет отдельного слоя описания, поэтому и парсер, и условия лежат рядом:

```go
func parseDate(s string) (time.Time, error) {
	return time.Parse("02.01.2006", s)
}

ready := rx.Compute(func() bool {
	a, err := parseDate(first.Get())
	if err != nil {
		return false
	}
	if mode.Get() == oneWay {
		return true
	}
	b, err := parseDate(second.Get())
	return err == nil && bookable(mode.Get(), a, b)
})
```

Обе версии получились примерно одного размера: 88 строк у Slint (61 `.slint` + 27 Rust) против 104 у Go. Комбо и оба поля дат в Go подписаны на `rx` через `Bind`, поэтому выбор режима и текст не требуют отдельных обработчиков. Тут декларативность не экономит код: правила всё равно пишутся руками, просто в Slint они лежат в выражении `enabled`, а в Go - в вычисляемом состоянии.

<Image src={booker} alt="Бронирование билета на gowt: выбор one-way flight, две даты и кнопка Book" quality="max" />

Любопытная деталь: невалидную дату Slint подсвечивает Rectangle поверх поля, потому что в декларативном UI наложение - обычное дело. В gowt поле подсвечивается через `SetBackground`, а панель настройки круга в следующей задаче стоит строкой под холстом - это выбор примера, а не ограничение фасада: виджет поверх рисунка кладётся через `CanvasView.AddChild` и `SetChildBounds`.

## Circle draw: модель против холста

Slint-версия держит список кругов как свойство, рисует их циклом `for circle[idx] in root.model`, а панель изменения диаметра накладывает поверх сцены в процентах от родителя. Rust хранит стек изменений из трёх вариантов: добавлен, удалён, изменён размер.

В gowt Canvas ничего не знает о модели: он рисует то, что лежит в слайсе, а обработчик мыши - опция фасада `gowt.OnMouseDown`. Попадание в круг всё равно считается вручную:

```go
func topmost(circles []circle, x, y int) int {
	for i := len(circles) - 1; i >= 0; i-- {
		r := circles[i].d / 2
		dx, dy := circles[i].x-x, circles[i].y-y
		if dx*dx+dy*dy <= r*r {
			return i
		}
	}
	return -1
}
```

История здесь - снимки состояния целиком, а не три типа изменений. Поэтому Go-версия короче (174 строки против 260), но грубее: снимок копирует весь список кругов на каждый сдвиг слайдера. Для учебной задачи это нормально, для редактора с тысячами объектов - нет.

## Slide puzzle: 688 строк описания против 332 строк рисования

Это самая показательная пара. Slint-версия - 453 строки `.slint` и 235 строк Rust: три темы, подписи, тени, скругления, анимации `animate px, py`, отдельная анимация "пинка", таймер auto play, проверка решаемости и фон с фотографией.

Go-версия - 332 строки: доска в массиве 4x4, обмен местами с дыркой, проверка решаемости и отрисовка на Canvas. Анимация - это тикер на 16 мс и easing вручную:

```go
t := 1.0
if animOn {
	t = min(1, float64(time.Since(animStart))/float64(animTime))
}
ease := 1 - (1-t)*(1-t)
```

Сравнение тут не в пользу Go по возможностям: в Slint анимация - свойство, в gowt - цикл, который надо не забыть остановить. Зато Go-версия не требует ни build step, ни отдельного языка: тот же `go build`, что и у остального проекта.

| temperature (gowt) | 13.8 МБ | 9.3 МБ |

На одинаковых задачах Go-бинарник после strip легче на 1.5-3.5 МБ. До strip разница меньше: оба тулкита тащат в бинарник свой рантайм, у gowt это порт SWT, у Slint - рендерер и рантайм. Выигрыша в разы нет ни у кого.

Три задачи 7GUIs (counter, temperature, timer) в репозитории Slint - это чистые `.slint`-файлы без своей Rust-обвязки, их запускает `slint-viewer`. Поэтому в таблице у них нет пары: сравнивать размер вьюера с приложением было бы нечестно.

## Память

### Slint и RSS процесса

RSS через 3 секунды после запуска окна, медиана из трёх прогонов, `ps -o rss`:

| Программа | RSS |
|---|---|
| counter (gowt) | 105 МБ |
| temperature (gowt) | 113 МБ |
| timer (gowt) | 123 МБ |
| booker: gowt / Slint | 107 / 104 МБ |
| circledraw: gowt / Slint | 113 / 103 МБ |
| slide puzzle: gowt / Slint | 123 / 120 МБ |

В этих трёх примерах RSS у Slint ниже на 2-10%. Физический след Slint мы не измеряли. Порядок величин один: сотня мегабайт на пустое окно у обоих, потому что RSS включает резидентные страницы системных библиотек, которые могут использовать несколько процессов.

### Контроль на чистом AppKit

Чтобы отделить AppKit от gowt, я сравнил одинаковые пустые окна 640x480 на Swift/AppKit и на gowt. M4 Max, macOS 27.2.1, семь пар запусков с чередованием порядка, замер через 3 секунды:

| | RSS, МиБ | Физический след, МиБ |
|---|---|---|
| Swift/AppKit | 79,05 | 18,58 |
| gowt | 103,83 | 32,08 |

RSS включает резидентные страницы системных библиотек, которые могут использовать несколько процессов. По физическому следу разница медиан составила 13,50 МиБ: это цена gowt и SWT поверх AppKit, а не всего стека.

### Версия важна

В сравнении со Swift я использовал gowt на коммите [e836eb5e](https://github.com/haiodo/gowt/commit/e836eb5e), это следующий коммит после v0.16.3. Раньше SWT при запуске создавал 15 временных нативных контролов для определения шрифтов. Теперь он запрашивает шрифт каждого типа при первом использовании. В пяти парных прогонах физический след счётчика снизился с 31,16 до 30,09 МиБ, таймера - с 48,08 до 46,28 МиБ. Это отдельный эксперимент от таблицы Slint.

## Сборка

Холодная сборка одного примера, кэши пакетов уже прогреты, но объектные файлы удалены:

| | Время | Что делается |
|---|---|---|
| gowt, `booker` | 8.6 с | компиляция gowt, стандартной библиотеки и примера |
| Slint, `booker` | 62 с | 252 крейта, включая сам Slint, рендерер и рантайм |

Rust-замер шумит: три холодных прогона на этой машине дали 36, 62 и 134 секунды, медиана - 62. Go стабильно 8.6. Разница в том, что у Go один компилятор и никакого кодогена, а у Slint `.slint` компилируется в Rust на этапе build script. Зато у Slint после первой сборки работает viewer с горячей перезагрузкой, а в Go каждое изменение интерфейса - это перезапуск приложения. Время инкрементальной сборки я не мерил: у Go это доли секунды, у Slint зависит от того, затронут ли `.slint`-файл.

## Что в итоге

Я не буду делать вид, что один тулкит победил. По коду разница около 10%, по RSS на одинаковых задачах Slint ниже на 2-10%, по размеру бинарника после strip Go легче на 1.5-3.5 МБ. На пустом окне 640x480 gowt занимает 32,08 МиБ физического следа против 18,58 у чистого AppKit: 13,50 МиБ - цена фасада и SWT.

Slint сильнее там, где интерфейс - это много состояний и переходов: биндинги, анимации, состояния и переходы описаны в одном месте, а не размазаны по обработчикам. Плата - отдельный язык, build step и компиляция 252 крейтов.

gowt сильнее там, где интерфейс - это нативные контролы и немного логики: таблицы, формы, инспекторы, панели. Плата - ручные подписки и ручная анимация на Canvas, а виджет поверх рисунка кладётся руками: `CanvasView.AddChild` и `SetChildBounds`. Ровно поэтому tenniarb, редактор диаграмм, написан на gowt: там важны нативные поля ввода и таблицы, а не плавные переходы.

Если бы я выбирал тулкит под новый проект на Go - взял бы gowt, потому что не хочу второй язык в проекте. Если бы проект был на Rust и с большим количеством анимаций - взял бы Slint. Оба варианта рабочие, и это, пожалуй, главный вывод.

Код: [7GUIs на gowt](https://github.com/haiodo/gowt/tree/main/examples/counter), [пазл на gowt](https://github.com/haiodo/gowt/tree/main/examples/puzzle). Оригиналы: [7GUIs у Slint](https://github.com/slint-ui/slint/tree/master/examples/7guis), [slide puzzle](https://github.com/slint-ui/slint/tree/master/examples/slide_puzzle), [описание задач 7GUIs](https://eugenkiss.github.io/7guis/).

Оговорки к замерам: одна машина, macOS, релизные сборки без профайлинга. RSS включает резидентные страницы системных библиотек, а физический след мерили только для пустых окон Swift/AppKit и gowt. В пазле на Go нет трёх тем и фото из Slint-версии, поэтому строка 332 против 688 описывает подмножество, а не полный порт.
