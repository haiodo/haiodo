# Commit Statistics

Скрипты считают коммиты автора по всем его репозиториям, берут цифры GitHub и рисуют SVG-графики для ретроспективы. Зависимостей нет: только Node.js, `git` и `gh`. Всё личное (автор, проекты, группы, импорты) лежит вне репозитория, в `config.mjs` папки данных; шаблон - `config.example.mjs`.

## Файлы

- `repos.mjs` - общие папки, помощники `local` и `gh`, правила файлов и загрузка `config.mjs` и `private-repos.mjs`; личных данных в нём нет
- `config.example.mjs` - шаблон личного конфига: автор, проекты и их порядок, импорты (`moves`), подписи строк, копии на GitHub, оценка, свои правила файлов
- `collect.mjs` - клонирует и обновляет репозитории, выгружает коммиты, классифицирует, пишет `commits.csv` и `summary.json`
- `github.mjs` - вклады GitHub по годам, доля копий, `github.json`
- `charts.mjs` - пять SVG: по кварталам, по годам, проекты, размер коммита, GitHub против уникальных
- `chart.mjs` - сборщик SVG и проверка подписей: вылет за viewBox, наложение подписей друг на друга и на пунктирную линию останавливает запуск ошибкой
- `csv.mjs` - чтение и запись CSV для остальных скриптов
- `scale.mjs` - логарифмическая шкала графика по кварталам: порог, высота столбца, метки
- `commits.test.mjs` - проверки классификации, CVS, оценки, квантилей, шкалы, регулярки автора и проверки подписей

## Требования

- Node.js 20 или новее
- `git` и `gh` (нужен `gh auth login`, GraphQL-запросы идут от имени пользователя)
- Папки (переменные окружения меняют умолчания):
  - `COMMITS_REPOS_DIR` - куда клонировать; без неё берётся `REPOS_DEFAULT` из `config.mjs`, а если он пуст, то `not-shared/commit-stats/repos`
  - `COMMITS_DATA_DIR` - CSV, JSON, выгрузка `raw/` и личные файлы `config.mjs` и `private-repos.mjs`, по умолчанию `not-shared/commit-stats/` (папка в `.gitignore`)
  - `COMMITS_ASSETS_DIR` - SVG, по умолчанию `src/assets/020/`

## Запуск по порядку

Сначала скопируйте `config.example.mjs` в `$COMMITS_DATA_DIR/config.mjs`: без него `collect.mjs`, `github.mjs` и `charts.mjs` останавливаются и пишут, где ждут файл.

```bash
node scripts/commits/collect.mjs   # клоны, выгрузка, commits.csv, summary.json
node scripts/commits/github.mjs    # github.json
node scripts/commits/charts.mjs    # SVG
```

Ключи `collect.mjs`:

- `--no-fetch` - не ходить в сеть за уже склонированными репозиториями
- `--reuse-raw` - пересчитать по выгрузке прошлого запуска (`raw/`), без git; так проверяют порядок проектов, `moves` и подписи
- `--big [проект ...] [--min-lines=15000] [--min-files=500]` - крупные коммиты, чтобы решить, какие из них импорты
- `--headers [проект ...] [--min-share=95]` - коммиты, в теме которых есть header, copyright, EPL или license, и доля заголовков среди их изменённых строк
- `--relations` - форки и шаблоны из GitHub API и общие корневые коммиты (`relations.json`); по ним расставляют порядок в `PROJECTS` файла `config.mjs`

Тесты: `node --test scripts/commits/commits.test.mjs`.

## Что считается

### Автор

Коммит берётся, если автор подходит по имени или по почте из `AUTHOR` в `config.mjs`. Совпадение проверяется по строке "Имя <почта>", поэтому однофамильца с другой почтой в список не добавляют.

### Выгрузка

- Коммиты: `git log --no-merges --numstat`, слияния: `git log --merges`, переименования считаются по новому пути
- Ветки: все (`--all`) без `refs/stash`, потому что stash - это merge-коммит под именем автора; для проекта можно задать свои `refs`
- Репозитории GitHub клонируются обычным `git clone`; полный клон, кроме проектов с `partial: true` (`--filter=blob:none`). Существующий клон только обновляется через `git fetch`, рабочее дерево не двигается
- Локальные репозитории (`local(...)` в конфиге) читаются на месте и не обновляются
- У проекта может быть несколько источников: коммиты объединяются по SHA до остальных правил

### Класс коммита (`kind`)

- `merge` - слияние, строк нет; в CVS-проектах так же помечены коммиты, которые только сообщают о слиянии ветки
- `duplicate` - уже учтён: внутри проекта тот же subject, те же числа строк и то же время автора (cherry-pick, перебазирование, копии истории с другими SHA), остаётся самый ранний; в CVS-проектах время не требуется, потому что конвертер его не сохраняет, там решают subject и числа; между проектами тот же SHA или тот же `at` (время автора, секунды) и subject в проекте, который стоит в конфиге раньше
- `move` - импорт или перенос уже существующего кода: первичная загрузка кодовой базы, вендорный дроп, перенос между репозиториями, массовое переименование, смена версии, обновление copyright, чужие патчи и их откаты. Это такие же коммиты автора, но строки в них написаны раньше или в другом месте, поэтому в код они не входят
- `work` - всё остальное

Дубликат остаётся строкой в `commits.csv`, чтобы было видно, что отброшено. В `summary.json` пары проектов лежат в `crossDuplicates`.

### Порядок проектов

Коммит, который есть в нескольких проектах (форки, зеркала, шаблоны, переписанные копии), считается в первом проекте списка. Поэтому апстрим стоит перед форками и копиями.

### CVS-проекты (`cvs: true`)

Клиент CVS в Eclipse коммитит каждый плагин отдельно, а конвертер CVS в git добавляет служебные коммиты. Для проекта с `cvs: true`, по порядку:

1. Коммиты конвертера ("file X was added on branch Y") выбрасываются из `commits.csv` и считаются в `excluded.cvs_artifacts`
2. Пустой коммит (0 файлов), чья тема только сообщает о слиянии ветки, становится `merge`
3. Работает обычная проверка дубликатов
4. Коммиты с одной темой, каждый не позже `CVS_WINDOW` секунд (10 минут) после предыдущего, сворачиваются в один: берутся хеш, дата и время первого, строки и файлы суммируются. Сколько строк свёрнуто, видно в `excluded.cvs_parts`
5. Коммит, чья тема только сообщает о слиянии ветки (один пункт, "merge with HEAD", "fixes from HEAD"), становится `merge` с нулевыми строками; его строки лежат в `excluded.cvs_merges`. Тема с другими пунктами ("merge with HEAD. Improved builder") остаётся `work`

### Строки

Строки каждого коммита делятся по пути файла:

- lock-файлы: `LOCK_FILES` в `repos.mjs`
- генерация, вендорный код и данные: общие правила `GENERATED_FILES` в `repos.mjs`, свои правила в `GENERATED_FILES` файла `config.mjs` и `generated` проекта, плюс Go-файлы с заголовком `// Code generated ... DO NOT EDIT` на HEAD
- код: остальное

Строки кода (`added`, `deleted`) считаются только по `work`. Строки `move` лежат отдельно (`move_added`, `move_deleted`) и на графике по кварталам идут отдельным рядом "переносы и массовые правки", который в код не складывается. Коммиты `move` входят в число коммитов везде: `commits_all` в `summary.json`, график по годам, график проектов. Варианты `_all` (`added_all`, `deleted_all`) - код и переносы вместе.

График `lines-by-quarter.svg` в логарифмической шкале. Добавленные строки лежат над осью, удалённые под ней, шкала зеркальная, 28 px на порядок; панель переносов использует ту же шкалу. Ось стоит на пороге `FLOOR` (100 строк, `scale.mjs`): квартал с числом строк не больше порога столбца не имеет, потому что логарифм нуля не определён. Скользящее среднее за 4 квартала тоже обрывается там, где оно не выше порога. Метки: 100, 1 тыс., 10 тыс., 100 тыс., 1 млн, верхняя метка - первая степень десяти не меньше максимума ряда.

### Импорты: как выбираются

`--big` показывает коммиты с 15 000 строк кода или 500 файлов. Коммит попадает в `moves`, только если тема или файлы показывают, что он приносит уже существующий код. Для коммитов с темой про заголовки лицензий есть `--headers`: коммит помечается, если заголовки составляют больше 95% изменённых строк (первый блок комментариев каждого файла). Рядом в конфиге пишется причина в одну строку. Крупный коммит без таких признаков остаётся `work`.

### Размер коммита

`summary.json`, `sizes`: по годам число, медиана, p25, p75 и среднее размера рабочего коммита (добавлено плюс удалено строк кода, без генерации и lock; переносы не входят). Квантиль - линейная интерполяция между соседними значениями. График `commit-size-by-year.svg` рисует медиану и полосу p25-p75 в логарифмической шкале; полый маркер - год меньше чем с 20 коммитами.

## Названия строк и метки

`group` проекта в конфиге задаёт название строки: оно стоит в колонке `repo` файла `commits.csv`, в `projects` файла `summary.json` и на графике проектов, поэтому панель, которая группирует по этой колонке, совпадает с графиком. Репозитории внутри строки остаются в `members` записи `summary.json`; число репозиториев с коммитами пишется в подписи строки на графике. Внутренние имена, порядок и источники проектов не меняются. `continuous: true` рисует строку одной полосой от первого до последнего коммита. `MARKS` ставит метку с датой на строку (форк, переезд).

## Выходные файлы

- `commits.csv` - `repo,date,at,month,hash,subject,kind,added,deleted,gen_added,gen_deleted,lock_added,lock_deleted,files` (`at` - время автора, секунды Unix), строки по дате
- `summary.json` - итоги, проекты (с `members` и `marks`), годы, кварталы, `estimate`, `sizes`, исключённое (слияния, дубликаты, импорты, генерация, lock, CVS), `crossDuplicates`
- `github.json` - вклады GitHub по годам и доля копий
- `relations.json` - связи между репозиториями
- SVG для MDX: `import Chart from '../../assets/020/lines-by-quarter.svg'`, затем `<Chart />`

## Приватность

Все закрытые проекты вместе называются `PRIVATE_LABEL`: так в `commits.csv`, `summary.json`, `relations.json` и во всех SVG. В `commits.csv` у таких строк хеш пустой, а subject - `PRIVATE_SUBJECT`. Репозитории, которые GitHub отдаёт как приватные, `github.mjs` суммирует под тем же названием. Промежуточные файлы в `raw/` настоящие, они лежат только в папке данных.

Личный конфиг и описание закрытых репозиториев не попадают в репозиторий. Они лежат в папке данных (по умолчанию `not-shared/commit-stats/`, в `.gitignore`): `config.mjs` для всего личного и `private-repos.mjs` для закрытых проектов. `repos.mjs` подключает их, если файлы есть. Формат `private-repos.mjs`: `export default [{ name, sources: [{ dir }], moves: [], generated: [], authors: { names, emails } }]`. Флаг `private` ставится сам, `generated` - регулярные выражения, которые добавляются к правилам генерации только для этого проекта. У проекта может быть несколько `sources`: копии и клоны одной истории объединяются по SHA, остальные повторы (одна тема и те же числа) идут в дубликаты. `authors` - дополнительные имена и почты автора в этом проекте: имя считается с любой почтой, почта с любым именем, голое имя без фамилии не подходит. Они читаются только из этого файла: домены почты выдали бы закрытые проекты. Тот же файл может добавить локальные копии проекта из `config.mjs`: `export const checkouts = { 'имя проекта': [путь или { dir, optional: true }] }`; имя несуществующего проекта останавливает запуск. Без `private-repos.mjs` скрипты работают только по публичным репозиториям.

Публичный репозиторий, чья история целиком или частично есть и в закрытом, ставят в `PROJECTS` перед `...privateProjects`: общие коммиты считаются в публичной строке.

## Как запустить на своих репозиториях

Чтобы повторить это на себе, возьмите `scripts/commits` (весь блог не нужен), скопируйте `config.example.mjs` в `$COMMITS_DATA_DIR/config.mjs` (по умолчанию `not-shared/commit-stats/config.mjs`, папка в `.gitignore`), поправьте и запустите три скрипта.

Агент для кода (Claude Code, Codex и другие) проведёт весь анализ на ваших репозиториях по навыку `commit-retrospective`: https://haiodo.github.io/skills/commit-retrospective/SKILL.md (в блоге файл `public/skills/commit-retrospective/SKILL.md`).

### Что настроить в `config.mjs`

Все экспорты, кроме `AUTHOR` и `PROJECTS`, необязательны; `GITHUB_LOGIN` нужен `github.mjs`.

- `GITHUB_LOGIN` и `AUTHOR` - логин, имена и почты автора
- `REPOS_DEFAULT` - папка клонов по умолчанию (меняется переменной `COMMITS_REPOS_DIR`)
- `PRIVATE_LABEL` и `PRIVATE_SUBJECT` - слова для закрытых проектов (по умолчанию русские)
- `PROJECTS` - функция `({ gh, local, privateProjects }) => [...]`: проекты в порядке "апстрим раньше форков", `local(имя, путь)` для локальных репозиториев, `gh(имя, 'владелец/репозиторий')` для GitHub; опции `moves`, `group`, `cvs`, `partial`, `generated`, `checkouts` (локальные копии той же истории, объединяются с клоном по SHA; запись `{ dir, optional: true }` молча пропускается, если папки нет, например отключён диск)
- `GROUPS` и `MARKS` - названия строк на графике проектов и метки на них; можно оставить пустыми
- `COPIES` - репозитории GitHub с одной историей (форк и его копии), чтобы вычесть повтор; пустой `repos` убирает вторую полосу
- `ESTIMATE` - оценка скрытых коммитов (ниже); пустой `fullTime` её отключает
- `GENERATED_FILES` - свои правила генерации, вендорного кода и данных; добавляются к общим из `repos.mjs`

Общие `LOCK_FILES`, `GENERATED_FILES` и `CVS_WINDOW` (окно для CVS) лежат в `repos.mjs`.

### Команды по порядку

```bash
export COMMITS_REPOS_DIR=~/repos               # куда клонировать, если не подходит REPOS_DEFAULT
node scripts/commits/collect.mjs               # клоны и commits.csv
node scripts/commits/collect.mjs --big         # крупные коммиты: импорты и переносы
node scripts/commits/collect.mjs --reuse-raw   # пересчёт после правки moves
node scripts/commits/github.mjs
node scripts/commits/charts.mjs
```

### Как найти импорты и решить, что это перенос

1. `collect.mjs --big` (можно с именем проекта) показывает коммиты с 15 000 строк кода или 500 файлов
2. Откройте коммит: `git show --stat <хеш>`. Перенос - это первичная загрузка кода, вендорный дроп, перенос между репозиториями, массовое переименование, смена версии, обновление copyright. Тема и список файлов должны это показывать; большой коммит с новым кодом остаётся `work`
3. Для заголовков лицензий запустите `--headers`
4. Впишите первые 10 символов хеша в `moves` проекта, рядом одной строкой причину, и пересчитайте с `--reuse-raw`

### Закрытые репозитории

Положите их описание в `$COMMITS_DATA_DIR/private-repos.mjs` (формат выше): в публичные файлы и графики попадёт только `PRIVATE_LABEL`.

### Оценка при полной занятости

Часть истории может лежать в закрытых репозиториях, поэтому годы без видимых коммитов дают заниженную картину. `ESTIMATE.fullTime` перечисляет эпохи, когда автор работал полный день и история видна, с годами; `hidden` - годы, когда коммиты ушли в закрытые репозитории.

- Среднее эпохи = все видимые коммиты (работа плюс переносы) в год по годам эпохи, в любых строках. Так линия среднего сравнивается с целыми столбцами графика, а закрытые репозитории тех же лет входят в среднее. Если эпоху нужно сузить, у неё задают `groups` или `projects`: тогда считаются только их строки
- Среднее при полной занятости A = среднее двух средних эпох
- Оценка года = max(0, A минус все видимые коммиты этого года)
- Итог оценки = сумма по скрытым годам
- Год, который резко выше остальных, не включают в эпоху: без него эпохи лучше сходятся
- Это верхняя граница для лет, когда автор руководил командами, а не писал код полный день: в такие годы часть времени уходила не в коммиты

На графике по годам A - штриховая линия, оценка - штрихованная часть столбца. Всё остальное - измерение. Диапазон low-high на графике не показывается: если эпохи сошлись случайно, узкий диапазон создал бы ложное ощущение точности. Расчёт лежит в `summary.json`, `estimate`: средние эпох, годы (видимые коммиты, оценка), итоги и определения; `low` и `high` (меньшее и большее среднее эпохи) оставлены для прозрачности, пояснение в поле `note`.

### Ограничения

- Коммиты CVS дробятся по каталогам, поэтому их число зависит от правила свёртки (`CVS_WINDOW`), а слияния ветки опознаются по теме
- Коммитер в CVS не всегда автор: чужие патчи, применённые автором, опознаются по теме и помечаются вручную
- Размер коммита зависит от эпохи: инструменты, привычки и форматирование меняют число строк в одном коммите
- Оценка скрытых коммитов - верхняя граница, а не измерение: она предполагает, что автор в закрытые годы работал так же много, как в годы с видимой историей
- Подписи графиков написаны по-русски прямо в `charts.mjs`; для другого языка правят их
